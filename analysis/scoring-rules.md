# 项目评分规则

## 概述

本规则用于评估 practice-repository 中各项目的质量和可重用价值，采用四维度评分体系，总分1-5分。

## 评分维度

### 1. 代码质量（30%权重）

| 分数 | 标准描述 |
|:---:|----------|
| 5 | 代码结构清晰，命名规范，注释完善，无明显bug，遵循SOLID原则 |
| 4 | 代码结构较好，命名较规范，有基本注释，少量可改进点 |
| 3 | 代码结构一般，命名基本规范，注释较少，存在一些代码异味 |
| 2 | 代码结构较差，命名不规范，注释缺失，存在明显问题 |
| 1 | 代码结构混乱，难以理解和维护 |

### 2. 架构设计（25%权重）

| 分数 | 标准描述 |
|:---:|----------|
| 5 | 架构设计优秀，模块化清晰，职责分离明确，扩展性强，符合最佳实践 |
| 4 | 架构设计良好，模块划分合理，有一定扩展性 |
| 3 | 架构设计一般，有基本的模块划分，但存在耦合问题 |
| 2 | 架构设计较差，模块划分不清晰，耦合度高 |
| 1 | 缺乏架构设计，代码组织混乱 |

### 3. 文档完整性（25%权重）

| 分数 | 标准描述 |
|:---:|----------|
| 5 | 文档完整，包含README、API文档、设计文档、使用说明 |
| 4 | 文档较完整，有README和基本使用说明 |
| 3 | 文档一般，有基本README，内容较简略 |
| 2 | 文档较少，仅有简单说明 |
| 1 | 缺乏文档，难以理解项目用途和使用方式 |

### 4. 可维护性（20%权重）

| 分数 | 标准描述 |
|:---:|----------|
| 5 | 易于维护，有单元测试覆盖，代码可读性强，有持续集成配置 |
| 4 | 较易维护，有部分测试，代码可读性较好 |
| 3 | 维护难度一般，测试覆盖不足，代码可读性一般 |
| 2 | 维护难度较大，缺乏测试，代码较难理解 |
| 1 | 难以维护，无测试，代码混乱 |

## 评分计算公式

**综合评分 = 代码质量 × 0.3 + 架构设计 × 0.25 + 文档完整性 × 0.25 + 可维护性 × 0.2**

评分结果保留一位小数。

## 评分等级对应

| 综合评分 | 等级 | 描述 |
|:---:|------|------|
| 4.5 - 5.0 | A | 优秀项目，强烈推荐重用 |
| 3.5 - 4.4 | B | 良好项目，可考虑重用 |
| 2.5 - 3.4 | C | 中等项目，需改进后重用 |
| 1.5 - 2.4 | D | 较差项目，谨慎使用 |
| 1.0 - 1.4 | E | 差项目，不建议重用 |

## 可重用程度判定

| 等级 | 可重用程度 | 说明 |
|------|----------|------|
| A | 高 | 可直接作为核心组件重用 |
| B | 高 | 可作为参考或基础组件重用 |
| C | 中 | 需要一定程度改造后重用 |
| D | 低 | 仅可参考部分代码 |
| E | 低 | 不建议重用 |

## 评分流程

1. **信息收集**：阅读项目文档和代码结构
2. **维度评分**：对四个维度分别打分（1-5分）
3. **计算总分**：使用公式计算综合评分
4. **确定等级**：根据总分确定等级和可重用程度
5. **记录理由**：记录每个维度的评分理由和项目优缺点

## 评分注意事项

- 评分应基于客观事实，避免主观臆断
- 对于信息不全的项目，应在备注中说明
- 评分结果应与项目实际情况相符
